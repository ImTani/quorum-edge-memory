How the system fits together.

Tanishk's device · one Python process

For this round both laptops run on one machine as separate processes, each with its own shard. "Offline" is a per-device switch that cuts hub traffic at the transport; everything else keeps running.

Three vectors per claim: text for meaning · bm25 for keywords · key for what it's about (entity + attribute, never the value).

Qdrant finds claims about the same thing.

  1. Every new claim, typed or pulled from the hub, runs one query on the key vector.
  2. Filtered to the same attribute and live claims; threshold 0.82.
  3. Same thing, different value → a conflict. Nothing is overwritten.
  4. Both laptops agree without talking: the conflict id is a hash of the two claim ids.
  5. The task's owner keeps one; the other is kept as history; the decision syncs.

FAQ: design

Why a separate key vector?
A conflict is "same thing, different value", so matching must ignore the value and the wording. The key is just entity + attribute.
Why not let the LLM decide conflicts?
Two laptops must reach the same conflict on their own. That needs a deterministic rule: same vectors, same query, same threshold, same id. The LLM only extracts.
Why does the demo show similarity 1.00?
Both mentions were matched to the known task "Sharma wedding edit", so the key text is identical. Worded differently, it's 0.85–0.90.
Why templated answers?
Milliseconds, no hallucinated facts, and every sentence cites a claim.

FAQ: limits

What if the model misreads a date?
It never computes dates; code resolves them from the message. And a wrong claim can't overwrite anything: it shows up as a conflict with both sources.
Three devices? Clock skew?
Detection scales: each device finds the same conflict. The sync cursor uses device clocks; the fix is a hub-assigned sync stamp.
Does it scale?
Each question is one hybrid query or one filtered nearest-neighbour search, which is what Qdrant is built for. We haven't benchmarked large memories yet.
Business model?
Per team, per month; no price set yet. Customer zero is BKA, a four-person production house and developer group.

Capture: from a message to a claim.

  1. POST /api/ingestnote, email or WhatsApp text with author and time.
  2. ExtractOllama returns JSON (entity, attribute, value phrase). Known entity names are passed in so "Sharma delivery" snaps to "Sharma wedding edit". 6 s budget.
  3. GroundDates resolved in code against today; values must appear in the text. Nothing usable → regex fallback.
  4. Build the claimOwner inherited from the existing entity; tier capped at the entity's widest tier; the best sentence becomes the cited excerpt.
  5. Storememory.add_claim: text, key and bm25 vectors, then flush. Team or my-devices claims go to the outbox.
  6. Checkconflicts.check runs the key-vector query; a disagreement opens a conflict.
  7. Publishclaim, conflict and activity events stream to the UI over SSE.

Search and answers: one query, on the laptop.

the query (memory.search)

QueryRequest(
  prefetches = [
    Nearest(bm25_query(q), using="bm25", limit=20),
    Nearest(dense(q),      using="text", limit=20),
  ],
  query  = Fusion.Rrf(k=60),
  filter = status ∈ {active, disputed}
           (+ tier == team in team view),
  limit  = 6)
  • Why hybrid: BM25 catches names and rare tokens ("Kapoor", "Pangong"); dense catches meaning ("due" ≈ "delivery").
  • Why RRF: the two scores live on different scales; rank fusion needs no calibration.
  • Answers are templated from the hits: disputed claims lead with both sources; "due this week" lists dated claims in the next 7 days.
  • 7–70 ms end to end. No model in the answer path, so no hallucinated facts.

Conflict engine: deterministic on every laptop.

detection (conflicts.check)

candidates = Nearest(key_vector(claim), using="key")
  filter: attribute == claim.attribute
          status ∈ {active, disputed}
          claim_id != claim.claim_id
  score_threshold = 0.82,  limit = 5

conflict if  value differs
         and names share a distinctive word

conflict_id = "cfl_" + sha1(sorted ids)[:10]
  • Same id everywhere: both laptops compute the same pair and hash, so they agree without exchanging conflict records.
  • "Disputed" stays local and doesn't bump versions, so it can't outrank a real update pulled later.
  • Owner only may resolve (403 otherwise); a lock makes double clicks settle once.
  • Resolution is a claim: winner active, loser superseded (both version-bumped), plus a resolution claim that syncs; others apply it.

Sync engine: outbox up, cursor down.

PushEvery second: peek the outbox, read each claim's current payload and vectors, drop anything device-only, upsert oldest change first in batches of 64. Point ids are uuid5(claim_id), so retries are idempotent; acks check a gen counter.
PullScroll the hub for modified_at > cursor, not modified by me, team (or my own my-devices). New claim → store with its vectors, then run conflict detection. Known claim → apply only if its version is newer.
Transport hookOne middleware on the qdrant-client transport refuses every request while offline and counts request and response bytes. Hub errors back off up to 5 s; the outbox keeps everything.

Concurrency and failure handling.

Shared shardAPI threads and the sync thread share one Edge shard behind a re-entrant lock; every write flushes (~28 ms), so a hard kill loses nothing.
SQLiteWAL mode, one connection serialised by a lock. The outbox survives restarts.
One sync round at a timeA round lock; a pull applies under one batched flush, and the cursor is saved only after it lands.
Hub downBackoff to 5 s, "Hub down" in the UI, the collection is re-created if the hub came back empty.
Model down or slow6 s budget per message; after a connection error the model is skipped for 20 s and the regex fallback runs.
Live UISSE with a 15 s heartbeat; the page reloads state and reconnects on drop.
Known limitsThe pull cursor uses device clocks (fix: a hub-assigned stamp); conflicts are pairwise; the hub has no auth yet.
